# Aster Stage 4 设计（主板受控进化 · Spec）

- 日期：2026-11-04
- 需求输入：`product_requirement.md` §9（受控进化）、§19 第四阶段
- 状态：**待用户批准执行**

## 1. 目标与诚实边界

让主板从运行数据里发现自身瓶颈，提出可验证的改进并安全应用。**v1 进化范围仅限可逆参数**：能力启停/排序权重/版本回滚/路由策略配置——**不含主板自我修改代码**（PRD §9.2 允许逐步探索，§20 明示"主板不受限修改自身规则"不在承诺内；代码级进化属远期）。

## 2. 核心 loop（PRD §9.4 七步映射）

```
瓶颈识别（数据）→ 提案（假设+方案+验收标准冻结）→ 隔离实验（回放集 A/B）
→ 独立评估（按冻结标准）→ 审批（分级）→ 小范围应用 → 监控与回滚
```

1. **瓶颈识别**：定期分析 capability_stats + 失败任务 + lessons——规则触发（某能力成功率<60% 且调用≥5；同类失败步骤重复≥3 次），LLM 归因（能力问题/协作问题/规划问题——PRD §9.3 先归因再动手）
2. **提案表**：问题证据（数据快照）、假设、方案（参数变更清单）、影响范围、**验收标准（落库后系统只读，仅人工可改——防放宽标准制造假进步，PRD §9.5）**、风险级
3. **回放集**：固定评估任务快照（replay_set）——改进前后各跑一遍，同任务同标准对比；保留一组不参与调试的对照任务
4. **风险分级审批**（映射既有网关）：低（排序/展示类参数）→ 自动应用+观察；中（路由策略/能力启停）→ 实验通过后仍需用户确认；高（涉及权限/审计/安全配置）→ **硬编码不自动，走 L2**
5. **应用与回滚**：变更前存配置快照；观察期同类指标退化 → 一键回滚（复用 capability_versions 回滚机制）

## 3. 数据模型（迁移 0004）

```
improvement_proposals(id, evidence_json, hypothesis, change_json, scope, risk,
  acceptance_frozen, status, experiment_result_json, applied_at, snapshot_json, created_at)
replay_set(id, name, task_goal, category, is_control, last_result_json)
```

## 4. 触发形态

不驻留进化 agent：v1 为**手动/定时触发的一次性分析任务**（复用 watchlist 巡检线程节奏），产出提案进待办中心等用户——进化是"提案-审批-实验"流程，不是自主改造。

## 5. 验收（PRD §21 主板进化行）

1. 人工注入劣化数据（如某能力成功率骤降）→ 系统识别并归因出提案
2. 提案走完"实验（回放对比）→ 冻结标准评估 → 分级审批 → 应用"全链
3. 回滚演示：应用后指标退化 → 快照恢复
4. 防作弊演示：系统尝试放宽验收标准被只读约束拒绝
5. 高风险变更（如停用审计）永不自动应用

## 6. 风险

| 风险 | 应对 |
|---|---|
| 单人数据量小，瓶颈识别噪声大 | 规则阈值偏保守（≥5 调用才评估）；LLM 归因仅出提案不出结论 |
| 回放集成本（LLM 调用） | 集固定 ≤10 条；实验由用户批准后才跑 |
| 进化流程自身复杂度失控 | v1 只有参数进化；代码级进化明确不做 |
